## Структура данных снабжения (бэкенд)
- `requests` (заявка) → `purchases` (закупка, 1:1 через request_id) → `payments` (оплата, 1:1 через purchase_id) → `shipments` (поставки, многие на закупку)
- Статусная модель с серверной проверкой переходов, идемпотентность везде (ON CONFLICT / условные UPDATE)
- RBAC: `src/rbac.js` — единственный источник правды, `ROLE_SECTIONS` (видимость) + `ACTIONS` (разрешённые действия)
- Роли: purchaseAnalyst(otabek) → localBuyer(nodira)/importBuyer(rustam) → supplyFinancier(bekzod) → cashier(kassir) → accountant(buh) → expeditor(exped) → supplyStorekeeper(sklad). director видит сводку. Все демо-пароли: `demo`

Это ломало ПРИ РЕАЛЬНОМ КЛИКЕ В БРАУЗЕРЕ: согласовать/отклонить заявку, исполнить оплату,

то есть большую часть основного workflow снабжения.

app.inject() напрямую - это не настоящий HTTP fetch и не воспроизводит точную семантику
Content-Type заголовков браузера. Весь день я проверял действия через curl (руками
задавал заголовки правильно) и через app.inject() тесты - ни один из способов не
воспроизводил реальный баг браузера. Нашёл только когда реально кликал кнопку в Playwright
и смотрел на 400 в консоли.

Урок на будущее: тестировать РЕАЛЬНЫЙ клик в браузере для каждого типа действия (с телом
и без тела отдельно), не полагаться только на backend-тесты или curl с ручными заголовками.
