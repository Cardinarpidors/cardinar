# План бэкенда Cardinar (старт с контура снабжения)

Статус: черновик для согласования. Цель — превратить статический демо-прототип в систему,
проходящую критерии приёмки ACC-01..21 из ТЗ (docs/TZ-cardinar-2026-09-23.md). Начинаем с контура
снабжения, архитектуру делаем расширяемой на остальные контуры (производство, продажи, B2B, HR, дашборд).

## 1. Зачем нужен бэкенд (что нельзя закрыть статикой)
- ACC-01: серверная проверка прав. Сейчас доступ гейтится только на клиенте (allowed()), ТЗ прямо
  говорит: скрытие кнопки без серверного ограничения защитой не считается.
- ACC-04/05/06/18: реальный обмен с 1С ERP, устойчивые уникальные ID, защита от дублей и
  восстановление после потери связи.
- ACC-10: сохранение данных при ошибке обмена и безопасная повторная отправка.
- Аудит на сервере, шифрование, разделение сред (ТЗ п.16).

## 2. Рекомендуемый стек
- Backend: Node.js + Fastify (или NestJS для более строгой структуры), TypeScript.
- БД: PostgreSQL (операции, статусы, аудит, идемпотентность). Redis — очередь обмена и блокировки.
- Auth: собственный логин + JWT/сессии, серверный RBAC по матрице ролей ТЗ. Позже — интеграция с
  учётками заказчика.
- Интеграция с 1С ERP: отдельный интеграционный сервис (адаптер), общается по API, который заказчик
  предоставит на стороне 1С/внешних программ (ТЗ: API формируется на их стороне, мы подключаемся).
- Фронтенд: текущий vanilla-прототип переиспользуем как UI, постепенно подключаем к API вместо localStorage.
  При росте — миграция на компонентный фреймворк по согласованию (не обязательна для приёмки).

## 3. Архитектура
- API Gateway (Fastify): аутентификация, серверная авторизация по ролям/разделам/складам/участкам.
- Доменные модули по контурам; первый — Supply (снабжение): needs, requests, approvals, purchases,
  payments, suppliers, logistics, customs, warehouse, stock, movements, documents, reminders, audit.
- Integration layer (1С): белый список операций (чтение справочников; запись расхода/выпуска/брака/
  перемещения/приёмки). Каждая операция — устойчивый уникальный ID (UUID), идемпотентность по этому ID,
  статусная модель: подготовлено -> ожидает -> отправлено -> принято 1С -> ошибка -> отменено.
- Очередь обмена (Redis/PostgreSQL): ретраи с backoff, фиксация времени последней успешной синхронизации,
  уведомление ответственных при ошибке.
- Audit log (PostgreSQL, append-only): вход, создание, изменение, подтверждение, отправка, повтор, результат.

## 4. Этапы (по ТЗ этап 1-2 + пилот снабжения)
1. Обследование снабжения и 1С: доступы, карта операций 1С, справочники, реальные роли/склады. -> карта интеграции.
2. Интеграционный фундамент: аутентификация, серверный RBAC, справочники, очередь обмена, тестовый адаптер 1С,
   разделение сред dev/test/prod, бэкапы. -> безопасный каркас.
3. Пилот снабжения: перенос сквозной цепочки заявка -> согласование -> закупка -> оплата -> исполнение ->
   отражение в 1С -> приёмка склада на серверную логику; идемпотентность, аудит, статусы обмена. -> рабочий
   пилот контура снабжения на реальных данных.
4. Приёмка снабжения по применимым ACC (01,04,05,06,07,10,16,17,18) на тестовой инфраструктуре.
Далее аналогично подключаются остальные контуры.

## 5. Что нужно от заказчика (блокеры старта)
- Тестовые доступы и техописание 1С ERP; перечень объектов/операций 1С для чтения и записи; карта
  интеграции (какое событие -> какой документ 1С).
- Реальные справочники: склады, участки, номенклатура, поставщики, единицы измерения.
- Окончательная матрица ролей и прав (раздел 5 ТЗ) — до пилота.
- Требования к размещению (сервер заказчика), нагрузке (число одновременных пользователей), хранению,
  резервному копированию.

## 6. Роль текущего демо
Демо-прототип остаётся как утверждённый макет UI и сценариев показа. Он не выбрасывается: на его основе
формируются экраны, а данные постепенно переезжают с localStorage на API. Это снижает риск и ускоряет пилот.
